# README - Apple Tree Sequence Modeling Project with Original Data

## Introduction

This project is a continuation of the work carried out with the "Transformer Pommiers" repository. The main objective here is to revisit transformer-based modeling, but this time using **real apple tree development sequences**. These real sequences are the ones that were initially used to create the Markov model, whose generated data was then used as a source for the aforementioned "Transformer Pommiers" repository.

This repository offers the flexibility to train a transformer model:
-   Either **from scratch** using this original data.
-   Or by **fine-tuning** a pre-trained model (although the fine-tuning logic is not explicitly detailed here, the structure would allow for it).

One of the major interests is to be able to **compare the performance and quality of the generated sequences** by a transformer trained on real data against:
1.  The real data itself (to assess model fidelity).
2.  Data generated by the Markov model (present in `markov_python_generated_dataset10000.csv`).
3.  Data that would be generated by a transformer trained on data from the Markov model (present in `generated_dataset.csv`).

The provided code allows for preprocessing these original sequence data, training transformer models, generating new sequences, and validating their quality.

## General Operation

### 1. Data Preprocessing (`pre_treatment.py`)

The `pre_treatment.py` script is responsible for reading the original sequence files (usually in `.seq` format).

-   **Sequence Extraction**:
    -   `.seq` files contain blocks of information. Each block represents the observations of a branch over several years.
    -   The script parses these blocks to extract series of numbers. A typical series is a line of 7 numbers. The 7th number of each series is interpreted as a "digit" of the sequence (0, 1, 2, 3, 4).
    -   The sequence is formed by concatenating these digits. For example, if the 7th numbers are `1`, `1`, `2`, `0`, the sequence will be `"1120"`.
    -   Each sequence is associated with an initial observation type (e.g., `LARGE`, `MEDIUM`) and a starting year (`Y1` to `Y5`). This information is extracted from the first series of each block.
    -   Sequences with a length less than 4 are filtered and removed.
-   **"Terminal Fate" Calculation**:
    -   For each extracted sequence, a "Terminal Fate" is calculated.
    -   The terminal fate is a prediction of the type of organ that will end the sequence, based on the year and the initial observation type.
    -   This is done using a predefined probability distribution in the `TerminalFate` class. The `terminal_fate` function samples a fate from this distribution.
-   **Saving to CSV**:
    -   All extracted sequences (with their type, year, and terminal fate) from all `.seq` files in a directory are combined into a single CSV file, typically `data/all_sequences.csv`. This file serves as the basis for training and validation.

### 2. Data Preparation for Transformer Training

This section describes how sequential data, initially preprocessed by scripts like those in `pre_treatment.py` and stored (e.g., in `data/all_sequences.csv`), are specifically prepared by the `PommierDatasetDecoderOnly` class (defined in `PommierDataset.py`) for training a decoder-only Transformer model.

The following steps are performed within `PommierDatasetDecoderOnly`:

-   **1. Initial Data Loading and Filtering:**
    -   Sequences are loaded from the specified CSV file (`dataset_path`).
    -   Strict filtering is applied: only rows where the "Observation" attribute is "MEDIUM" AND the "Year" attribute is 'Y4' or 'Y5' are kept for further processing.

-   **2. Detailed Sequence Tokenization (`tokenize_row`):**
    -   Each retained sequence is broken down into a list of tokens.
    -   This tokenization follows specific rules:
        -   A base vocabulary of accepted tokens is defined: `["LARGE", "MEDIUM", "SMALL", "DORMANT", "FLORAL", "Y1", "Y2", "Y3", "Y4", "Y5"]`. Sequence elements corresponding to these tokens are kept as is.
        -   If a sequence element is a string composed only of digits (e.g., "123"), it is segmented into individual tokens for each digit (e.g., `['1', '2', '3']`).
        -   Any other type of element is ignored.
    -   For example, a raw data row might be transformed into a list of tokens like `['Y4', 'MEDIUM', '1', '2', '3']`.

-   **3. Vocabulary Construction and Conversion to Numerical IDs (`build_vocab`):**
    -   If a `token_to_id` dictionary is not provided during initialization, a new vocabulary is built from the set of unique tokens from all tokenized sequences.
    -   Two special tokens are systematically added to this vocabulary:
        -   `<PAD>`: Padding token, used to equalize the length of sequences within a batch. Its ID is usually 0.
        -   `<SOS>`: Special "Start of Sequence" token. Its precise role in forming input sequences is described below.
    -   *Important note:* Based on the available code analysis and information from our conversation, an `<EOS>` (End of Sequence) token is not explicitly added to the vocabulary or sequences by the `PommierDatasetDecoderOnly` logic at this stage.
    -   After vocabulary construction, each token in the token lists is replaced by its corresponding numerical ID.

-   **4. Creation of Input and Target Sequences for the Decoder-Only Model (`__getitem__`):**
    -   The goal of a decoder-only Transformer model is to predict the next token in a sequence. For this, pairs of (input, target) sequences are generated from each ID sequence.
    -   The specific logic implemented in `PommierDatasetDecoderOnly` is as follows:
        1.  Consider an original token sequence, for example `S_orig_tokens = ['Y4', 'MEDIUM', '1', '2', '3']`. After conversion to numerical IDs (where `id_TOKEN` represents the ID of TOKEN and `id_SOS` the ID of the `<SOS>` token), this gives `S_orig_ids = [id_Y4, id_MEDIUM, id_1, id_2, id_3]`.
        2.  The ID of the `<SOS>` token is inserted *after the first two tokens* of `S_orig_ids`. The modified ID sequence, `S_mod_ids`, becomes `[id_Y4, id_MEDIUM, id_SOS, id_1, id_2, id_3]`. This corresponds to a token sequence `S_mod_tokens = ['Y4', 'MEDIUM', '<SOS>', '1', '2', '3']`.
        3.  From `S_mod_ids`, the input and target sequences are formed:
            -   `input_sequence_ids = S_mod_ids[:-1]`, which gives `[id_Y4, id_MEDIUM, id_SOS, id_1, id_2]`.
                -   The corresponding token sequence given as input to the model is: `['Y4', 'MEDIUM', '<SOS>', '1', '2']`.
            -   `target_sequence_ids = S_mod_ids[1:]`, which gives `[id_MEDIUM, id_SOS, id_1, id_2, id_3]`.
                -   The corresponding token sequence that the model must learn to predict is: `['MEDIUM', '<SOS>', '1', '2', '3']`.

        -   **Impact of Trimming in the Training Loop (`pipeline.py`):**
            -   It is crucial to note that during the training phase (as seen in `pipeline.py`), the logits (raw model outputs) and target sequences are trimmed before calculating the loss: `logits_trim = logits[:, 2:, :]` and `targets_trim = target_seq[:, 2:]`.
            -   This means that the first two elements of `target_sequence_ids` (i.e., `id_MEDIUM` and `id_SOS` in our example) are **not** used for loss calculation. Similarly, the model's corresponding predictions for these first two target tokens are ignored.
            -   Therefore, effective learning begins with predicting the token that follows the `<SOS>` token in the `S_mod_tokens` sequence.
            -   Revisiting our example `S_mod_tokens = ['Y4', 'MEDIUM', '<SOS>', '1', '2', '3']`:
                -   The effective input for the first relevant prediction is `['Y4', 'MEDIUM', '<SOS>']` (the first three tokens of `input_sequence_tokens`).
                -   The model learns to predict `'1'` (the fourth token of `S_mod_tokens`, which is the first token of `targets_trim`).
                -   Then, with the input `['Y4', 'MEDIUM', '<SOS>', '1']`, it learns to predict `'2'`.
                -   And with `['Y4', 'MEDIUM', '<SOS>', '1', '2']`, it learns to predict `'3'`.

-   **5. Batch Collation and Padding (`collate_fn_decoder_only`):**
    -   When data is loaded by a `DataLoader`, the `collate_fn_decoder_only` function is used.
    -   Its role is to group multiple `(input_sequence_ids, target_sequence_ids)` pairs into a batch.
    -   Since sequences can have different lengths, they are padded with the ID of the `<PAD>` token (value 0) to achieve a uniform length within the batch, usually the length of the longest sequence in the batch.

-   **6. Weight Calculation for Stratified Sampling (`WeightedRandomSampler`):**
    -   To potentially mitigate imbalances between different sequence categories (based on "Observation" and "Year" combinations), `PommierDatasetDecoderOnly` calculates weights.
    -   Each sequence is assigned a weight that is the inverse of the frequency of the group to which it belongs (`weight = 1.0 / number_of_sequences_in_the_group`).
    -   These weights can then be used by a `WeightedRandomSampler` in the `DataLoader` (configured in scripts like `pipeline.py` or `main.py`) to oversample sequences from underrepresented groups during the training phase.

This meticulous data preparation is crucial for the effective training of the Transformer model.

### 3. Validation of Generated Sequences (`SimpleValidator.py`)

The `SimpleValidator` class is crucial for evaluating the quality of sequences generated by the models by comparing them to the sequences in the original dataset. It takes as input the paths to the CSV files of the datasets to be compared (e.g., original data and generated data).

-   **Initialization and Filtering (`__init__`, `filter_and_include_all_if_present`):**
    -   During initialization, one can specify whether validation plots should be displayed (`show_plots`).
    -   The `filter_and_include_all_if_present` method is an important preparation step. It ensures that the comparison is made on a fair basis:
        1.  It identifies the (`Observation`, `Year`) pairs that are present in **all** provided datasets.
        2.  For these common pairs, it keeps **all** associated sequences from each dataset. There is no equalization of the number of sequences between sources at this stage for these common pairs.
        -   The goal is to compare the complete distributions for the (Observation, Year) conditions where all models were able to produce data.

-   **Detailed Validation Methods:**

    1.  **`sequence_length_validation(dataframe)`**:
        -   **Objective**: Compare the average length and standard deviation of sequences.
        -   **Operation**:
            -   For each common (`Observation`, `Year`) pair, it calculates the length of each sequence.
            -   It then groups by `Source` (dataset name) and calculates the mean and standard deviation of the lengths.
            -   **Visualization**: A scatter plot is generated for each (`Observation`, `Year`) pair. Each point represents a `Source`, with its average length on the y-axis and error bars indicating the standard deviation. This allows for checking if the average lengths are similar and if the variability (standard deviation) is comparable.

    2.  **`sequence_length_distribution_validation(dataframe)`**:
        -   **Objective**: Compare the complete distribution of sequence lengths.
        -   **Operation**:
            -   For each common (`Observation`, `Year`) pair:
                -   Calculates the length of each sequence.
                -   Generates probability density histograms of lengths for each `Source`.
                -   Superimposes kernel density estimates (KDE) to smooth the distributions.
                -   Calculates the **Jensen-Shannon (JS) distance** between the KDE distributions of each pair of sources. JS distance measures the similarity between two probability distributions (a lower value indicates greater similarity).
            -   **Visualization**: One plot per (`Observation`, `Year`) pair showing the histograms and superimposed KDE curves. The calculated JS distances are stored and can be displayed.

    3.  **`sequence_digit_stats(dataframe, observation_filter=None, year_filter=None)`**:
        -   **Objective**: Analyze the frequency of each digit (0 to 4) in the sequences.
        -   **Operation**:
            -   For each (`Observation`, `Year`) pair (possibly filtered):
                -   For each digit (0, 1, 2, 3, 4):
                    -   For each `Source`, it counts the number of occurrences of the digit in each sequence.
                    -   It then calculates the mean and standard deviation of these counts for that `Source`.
                -   Calculates the absolute errors (differences) of the means and standard deviations between pairs of `Source`.
            -   **Visualization**: For each digit and each (`Observation`, `Year`) pair, a bar chart is generated. Each bar represents a `Source`, showing the average number of occurrences of the digit, with error bars for the standard deviation. The calculated errors between sources are often displayed as annotations.

    4.  **`sequence_series_analysis(dataframe, observation_filter=None, year_filter=None)`**:
        -   **Objective**: Analyze "series" of consecutive digits. A series is an uninterrupted sequence of the same digit (e.g., `111` in `01112`).
        -   **Operation**:
            -   For each (`Observation`, `Year`) pair (possibly filtered):
                -   For each digit (0 to 4):
                    -   For each `Source` and for each sequence from that source:
                        -   The `count_series` method is called. It identifies all series of the target digit in the sequence.
                        -   It returns: the number of series found, the average length of these series, and the standard deviation of the lengths of these series.
                    -   Then, for each `Source`, these statistics are aggregated across all its sequences:
                        -   Average number of series per sequence.
                        -   Average of the average series lengths.
                        -   Average of the standard deviations of series lengths.
                        -   Corresponding standard deviations for these aggregated averages are also calculated.
                -   Calculates the absolute errors for these aggregated statistics (average number of series, average series size, etc.) between pairs of `Source`.
            -   **Visualization**: For each digit and each (`Observation`, `Year`) pair, a grouped bar chart is generated. It shows, for each `Source`, the three aggregated metrics (average number of series, average series size, average standard deviation of series sizes), with error bars. The calculated errors are often displayed as annotations.

-   **Statistics Summary (`print_stats_summary`)**:
    -   Displays a summary of error statistics (JS distances, errors on digit and series stats) collected between the different sources for the (`Observation`, `Year`) pairs.

### 4. Training and Generation (Example with the Transformer - `main.py`)

The `main.py` file orchestrates the transformer model training and sequence generation.

-   **Configuration**: Defines model hyperparameters (embedding dimension, number of attention heads, etc.), training parameters (batch size, number of epochs, learning rate), and file paths.
-   **Data Loading**: Uses `PommierDataset` and `DataLoader` from PyTorch.
-   **Training**:
    -   Initializes the transformer model, optimizer, and loss function (CrossEntropyLoss).
    -   Training loop over several epochs.
    -   Uses `EarlyStopping` to stop training if the validation loss no longer improves.
    -   Saves the weights of the best model.
-   **Generation**:
    -   Loads the weights of the trained model.
    -   Calls the `generate_sequences` function (from `pipeline.py`) to produce a new dataset of sequences.
    -   The generated sequences are saved in a CSV file.

## How to Use
<!--  -->
1.  **Prepare the environment**:
    -   Ensure you have Python installed on your system.
    -   This project uses `uv` as a package and virtual environment manager. If you don't have it, install `uv` by following the instructions at [https://github.com/astral-sh/uv](https://github.com/astral-sh/uv).
    -   Once `uv` is installed, synchronize the environment and install all necessary dependencies (PyTorch, Pandas, NumPy, Plotly, Scikit-learn, UMAP, etc.) by running the following command at the root of the project:
    ```bash
    uv sync
    ```
    -   This will create a virtual environment (if it doesn't exist) and install the packages listed in `pyproject.toml` and `uv.lock`.
2.  **Preprocessing**:
    -   Place your `.seq` files in a directory (e.g., `data/`).
    -   Run `pre_treatment.py` (potentially adjusting the input directory in the script) to generate `data/all_sequences.csv`.
    ```bash
    uv run pre_treatment.py
    ```
3.  **Transformer Training**:
    -   Modify the configurations in `main.py` if necessary.
    -   Run `main.py` to train a new transformer model and generate sequences.
    ```bash
    uv run main.py
    ```
    -   The model weights and generated sequences will be saved in the `experiments/` directory and at the root respectively.
4.  **Validation**:
    -   Ensure you have at least two CSV files of sequences to compare (e.g., `data/all_sequences.csv` and `generated_dataset.csv` or `markov_python_generated_dataset10000.csv`).
    -   Modify the `dataset_paths` and `dataset_names` in the `main` function of `SimpleValidator.py` to point to your files.
    -   Run `SimpleValidator.py`:
    ```bash
    uv run SimpleValidator.py
    ```
    -   Validation plots will be displayed in your browser (if `show_plots=True`) and a summary of statistics will be printed to the console.
